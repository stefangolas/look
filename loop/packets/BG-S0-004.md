## Problem

Three property tests in `truck-stepio`'s `input` binary fail **deterministically**
today (verified: identical first failure across runs, no seed file involved):

- `b_spline_surface_with_knots` — first fails `assert_near!` at
  `geometry.rs:1416` with `left: 0.0, right: 73.7054250616019`, then panics
  during shrinking;
- `nurbs_surface_b_spline_surface_with_knots` — same shape;
- `nurbs_curve_b_spline_curve_with_knots` — panics
  `attempt to subtract with overflow at in/mod.rs:1939:20`, final report
  `The scalar 0 is not positive`.

Run them yourself before changing anything — watching them fail is part of the
job:

    cargo test -p truck-stepio --test input b_spline_surface_with_knots -- --nocapture

The mechanism, derived from the shrunk cases:

1. The test generators build cumulative knot vectors whose **active domain**
   `[T_degree, T_ctrl]` can collapse to a single value — this happens whenever
   the knot-multiplicity structure puts both endpoints of the domain inside one
   run of equal knots (shrunk witness: 7 distinct knots, all increments 0.001,
   all mults 1, degree 3, ctrl 3 → domain `[0.004, 0.004]`; the unshrunk
   witness had `udegree = 5`, mults `(2,1,1,3,1,2,1,1)` → `T_5 == T_6`). No
   floating-point rounding is involved: the knot values round-trip through STEP
   text exactly.
2. `ValidatedKnotVector::validate` correctly returns
   `DegenerateActiveDomain` for these.
3. Every spline import path then handles that failure with
   `Err(_) => quasi_uniform_knots(ctrl, degree)` — which either **silently
   substitutes a synthesized uniform knot vector for the source's** (the
   `0.0` vs `73.7` failure: the import "succeeds" as different geometry), or
   **panics** when `ctrl <= degree`: `num_ctrl - degree` underflows (debug) or
   `KnotVec::transform(0.0, 0.0)` trips its `scalar > 0.0` assert (release).

A secondary gap in the same paths: the **curve** import normalizes a
tiny-but-nonzero total knot range to `[0, 1]` before construction (an exact,
shape-preserving affine reparameterization — see the comment block above
`in/mod.rs:1880` and the landed test
`b_spline_curve_with_knots_tiny_knot_interval_converts`), but the **surface**
import has no such step, so `BSplineSurface::try_new`'s per-axis
`is_small_ratio(range_length())` refusal rejects any surface with one tiny axis
span outright — a well-formed source that cannot be imported at all.

## Decisions already made for you

1. **Every `validate` failure on an explicit-knots path is a typed refusal.**
   In `impl TryFrom<&BSplineCurveWithKnots> for BSplineCurve<P>` collapse the
   two `Err` arms (the `UnsortedRawKnots` early-return and the `Err(_)`
   fallback) into one: `Err(e) => return Err(e.into())`. Do the same for both
   axes in `impl TryFrom<&BSplineSurfaceWithKnots> for BSplineSurface<Point3>`.
   `StepConvertingError` is `Box<dyn std::error::Error>`, so `.into()` needs no
   new variant, and `SplineConstructionError` already carries a
   `SplineSourceWitness`. The rational forms (`RationalBSplineCurve`,
   `RationalBSplineSurface`) dispatch through these impls — do not touch them.

2. **Keep the curve-path tiny-range normalization exactly as it is**, and add
   its twin to the surface path, **per axis, independently**: after each
   `validate` succeeds, `if ctx.is_small_ratio(kv.range_length())` →
   `kv.transform(1.0 / range, -kv[0] / range)` with `range` computed once. You
   will need `let ctx = ToleranceCtx::unscaled_legacy();` in the surface impl.
   Copy the comment rationale from the curve path and adapt it to the axis
   wording. `validate` has already proved the active domain exceeds `1e-12`,
   and the active domain is a subinterval of the total range, so `range` is
   strictly positive and `transform` never divides by zero here — say so in
   the comment, as the curve path does.

3. **`quasi_uniform_knots` becomes total.** Change its signature to
   `fn quasi_uniform_knots(num_ctrl: usize, degree: usize) -> Result<KnotVec, StepConvertingError>`
   and guard `num_ctrl <= degree` by returning
   `SplineConstructionError::ControlPointCountMismatch { witness }` where the
   witness carries `degree`, `control_point_count: num_ctrl`, and empty
   `raw_knots` / `raw_multiplicities` / `expanded_knots` lists,
   `active_domain: (0.0, 0.0)`, `first_inversion_index: None`,
   `entity_id: None` — the same shape `validate` itself uses for the
   length-mismatch arm. Both types are re-exported by
   `truck_geometry::nurbs` (`pub use knot_vec::*`). Propagate with `?` at the
   remaining callers: `QuasiUniformCurve::try_from` and both calls in
   `QuasiUniformSurface::try_from`. Do not change the arithmetic of the happy
   path. Note this also closes a latent panic: `QuasiUniformSurface` on an
   empty control list previously reached `quasi_uniform_knots(0, v_degree)`.

## H-3, which is what rejected three packets in this family

GATE-2 fails any **added** line carrying a bare `1e-N` literal unless that same
line ends with an `// H-3` comment. It is a text gate on the diff: it does not
know your literal is a parameter value, and it does not care that the line is
in a test. The house form:

    assert!((got - ans).magnitude() < 1.0e-9, ...); // H-3: float slack between two evaluations of one tensor-Bernstein point, not a length

Every comparison epsilon you write gets a same-line `// H-3:` comment naming
the dimensionless quantity being compared. Knot values and parameter-space
coordinates are dimensionless and legitimate; a literal that really is a
model-space *length* does not get an opt-out. Run `bash scripts/kernel-gates.sh`
yourself before you write `RESULT.json`; it is the same script V4 runs. Note
that **rustfmt moves a trailing comment off a line that opens a brace** — if
that happens, extract the literal to its own statement line and mark that.
