## Problem

Extruding an `IntersectionCurve` — the variant Booleans produce — aborts the
process. `impl ToSameGeometry<Surface> for ExtrudedCurve<Curve, Vector3>`
reaches `unimplemented!()` when both rail curves are intersection curves.
Extruding an edge of a Boolean result is an ordinary modelling operation, so
this is reachable from untrusted geometry and violates house rule **H-1 — no
panics on data**.

## The scoping decision — read this before you plan

The obvious move is to change the trait method to return `Outcome<T>`. **Do not
do that.** It was measured on 2026-08-16: `to_same_geometry` has **34 impls
across 11 files and 63 call sites across 19 files**, including nine in
`truck-stepio`, which is the production STEP import path. That is a
signature-ripple refactor, not a Stage 0 abort fix, and it would collide with
two other crates being edited concurrently.

Instead, **add a fallible sibling to the trait** in
`vendor/truck/truck-geotrait/src/traits/mod.rs`:

```rust
pub trait ToSameGeometry<T> {
    /// Obtain a curve or surface that gives the same image as a given curve or surface.
    fn to_same_geometry(&self) -> T;

    /// The fallible form (BG-S0-003, H-2). Implementors whose conversion can
    /// fail on admissible input override this; the default delegates, so every
    /// existing impl keeps working unchanged.
    fn try_to_same_geometry(&self) -> Outcome<T> {
        Ok(Certified::new(self.to_same_geometry(), Certificate::float("to-same-geometry")))
    }
}
```

Check `truck_base::evidence` for the exact constructors — `Certified::new` and
the `Certificate` builder may be named differently. **Use what is actually
there**; do not invent a constructor, and do not edit `evidence.rs` (another
worker owns that file this wave).

Then the extrude impl overrides `try_to_same_geometry`, returning
`Refusal::UnsupportedEnvelope(EnvelopeCase::NonCanonicalCarrier)` for the
`(IntersectionCurve, IntersectionCurve)` pair and delegating everything else.

**`to_same_geometry` itself must stop panicking too.** For the pair arm it needs
*some* total behaviour. It is a trait method with no error channel, so the only
honest options are to return a documented degenerate surface or to keep the
existing approximation path. Pick whichever the surrounding code supports,
document the choice in a comment naming BG-S0-003, and **say which you chose in
your `RESULT.json` notes** — this is the one judgement in the packet and a
reviewer needs to see it. If neither is defensible, that is a `SPEC_GAP`: stop
and write the two readings down.
